## What this is

Local Attest e-sign app implementing the three-party data model from `docs/esign-data-model.pdf`, without Google/GCS:

| Brief | Local |
| --- | --- |
| Postgres | SQLite (`server/data/attest.sqlite`) |
| GCS | `server/data/files/**` |
| Google Identity | Email and password on the server (shared SQLite) |
| Transactional email | SMTP (or Outlook on Windows) + outbox log |

Parent brand / sending company context: **Union Payroll** — https://union-payroll.ltd/

## Working product model

### Start

After login the screen asks one question: **working from the library**, or **sending a new contract**? The header no longer lists Companies, Templates, Library and New contract.

A new contract is four steps: broker from the saved list, the contract type — **3-way lower**, **3-way higher** or **4-way** (each option names the broker’s contract it will use, or says the placeholder is used; item 49) — schedules (the broker’s schedules for that type, all ticked to start), then the other parties (company, signatory, role, email). That pairing is saved into the library. The library path picks the saved broker and contractor, then asks the contract type, the schedules and the remaining parties.

Broker setup is where company details, the front cover, the back cover, and the brand SVG are added. Staff pages ask for email and password. Party signing and due-diligence links stay open. Library templates, companies and clients are rows in the server database, so any browser that can sign in sees the same records.

- **Due diligence pack** follows the worked example: broker cover with the contract’s own details stamped on it, company identity, an annex index with page numbers, then the documents. The same cover stamp is applied to the contract. Companies House filings and a UK Sanctions List check are fetched from the company number for the contractor and, on a 4-way, the supplier. The person adding that company attaches only what cannot be fetched. Contractor: VAT certificate, Employers’ Liability certificate, Public Liability certificate, Professional Indemnity certificate, PI policy schedule and wording, bank statement for the account paying workers and HMRC, illustrative payslip, and a payroll chain map with PAYE/ERN confirmation. Received and checked dates are entered on the contract, because they change with each client. No party is emailed to supply these or to sign the pack.
- **Companies House evidence is one page per fact (decided 2026-11-25):** the fetch keeps the incorporation filing, each change of name (the CERTNM, or the NM01 when there is no certificate that day), only the **latest** AD01, and a PSC01/PSC02 only for a PSC who is still active (matched by name in the filing description). PSC detail changes and cessations (PSC04, PSC05, PSC07) are not fetched; the narrative and disclosures cover them. The pack attaches only **page 1** of each filing (the certificate or notice); the IN01 application and model articles behind an incorporation certificate are left out. The full filing stays on the company record. There is no separate “Director details” annex page; officers are listed in the narrative. This took the worked-example test pack from 78 pages to 28 (the reference pack is 42 with real insurance documents).
- **Declarations and director’s certificate (decided 2026-11-25):** the broker’s director signs the certificate while building the pack, using the pack signature in the app. The pack generates a **Declarations** checklist per company (Result / Check / Annex columns: active, accounts and confirmation statement up to date, no sanctions match, each required document, all documents received and checked; the Annex column gives the annex letters that evidence each line), then **Disclosures** grouped by company in short lines (not active, overdue filings, incorporated under 12 months, name changed in 24 months, registered office moved in 12 months, officers appointed in 12 months or resigned in 24, PSCs ceased in 24 months, sanctions hits). Keep pack and app wording short: no lines that explain how the app works. Then the **Director’s certificate** page: “I, {broker signer}, {role} of {broker legal name}, certify that…” with four statements (reviewed Companies House, sanctions and annex; dates as in the index; HMRC standing evidenced by the contractor’s payroll chain map and PAYE/ERN confirmation, and the supplier’s HMRC PAYE registration letter; declarations and disclosures complete). The broker’s signature and the date are stamped into that box (no signing line, item 33). Packs compiled before this existed still get the old separate signature page.
- **Signed pack goes into the contract:** when the contract is sent (or a single party link is minted), the contract is baked again if the signed pack is not already in it, and the whole signed pack is added after the contract’s back cover as an extra document. `envelopes.baked_dd_sha256` records which pack hash is in the baked PDF.
- **Pack layout (2026-11-25):** generated cover in the worked example’s style (logo, broker name, “Due Diligence & Onboarding Pack”, “For use with the {broker} {contract}”, parties, pack reference, broker legal block), then narrative pages (one line each for number/status/incorporation, registered office, former names, accounts and confirmation statement as last date and next due date, sanctions result; officers; PSCs with short nature of control such as “shares 75%+” and ceased dates), declarations, disclosures and the director’s certificate, then the **annex index** as a table: annex letter, document, page range, received date, checked date, grouped by party. Then the documents and the broker’s back cover last. Dates print as dd/mm/yyyy. The sanctions evidence page lists every name and number searched (company, number, previous names, directors and PSCs, merged when Companies House lists the same person twice).
- **Client at Companies House (decided 2026-11-25):** on a new contract the Client has a company number and **Fill from Companies House**. It fills the legal name, number and registered office, and offers the active directors as the signatory (role Director). No filings, documents or sanctions check are fetched for the client: the client uploads its own incorporation certificate, VAT certificate and director ID when it signs. At bake, each party’s text boxes on the contract are pre-filled where the label names the company name, company/registration number, registered office or address, print/full name, or position/job title. Signers can still change them.
- The library stores a broker, a contractor and the cover. The contract is not chosen there: it comes from the broker and the shape when a contract is created (item 39). Staff reach it by answering “working from the library” on the start screen, not from a library form in the header.
- Each party is a company name, signee name, role (Director, or Authorised signatory) and email. The contract has a signature and a date for each party. The broker’s signature on the due diligence pack is that pack’s date.
- **Delete company** on the list and setup pages, with an in-app **Are you sure?** dialog (Cancel / Yes, delete). Soft-delete (`is_active = 0`); existing contracts stay on file.
- **Compliance company** — a third party sends the contract on behalf of the broker. The due diligence pack is built and signed in the app, not emailed out for completion. Its details, from address, mailbox, introductory email, and Gmail signature live on the broker’s Compliance company tab (and at Compliance company from the start screen). It has no Companies House number. The intro names the broker it is sent on behalf of, using `{{broker_name}}`; `{{compliance_name}}` is the compliance company’s own name; `{{other_parties}}` reads “the Contractor and the Client” on a 3-way and “the Contractor, the Supplier and the Client” on a 4-way. The setup page previews both shapes. Opening **Good morning** / **Good afternoon** still follows the computer clock. Paste from Gmail Settings → Signature keeps formatted HTML (text, links, fonts, images).

### Templates

- **Per broker (items 39 and 49):** each broker has a **3-way lower**, a **3-way higher** and a **4-way** contract, and its own **schedules**. The Templates page has one section per broker; the broker’s page has the same panel under **Contracts and schedules**. **Open / Replace / Delete** per file (same controls as company files), with a **Name in the pack** for each contract. Uploading a PDF scans for Client / Broker / Contractor signature and detail fields, and Supplier (SPV) when that word is on the page. Signing room lists those fields with **Jump to**.
- **Placeholder:** until a broker’s contract for a type is uploaded, the shared generated placeholder (“Master Services Agreement”, “three-party execution”) is used; it carries Supplier signature and date fields so 4-way contracts bake. No broker contracts are uploaded yet.
- Bake refuses a contract when any of its parties has no signature field, and names the party.
- **Schedules** — **Add schedule** asks for a name and **Used on** (a tick for each of 3-way lower, 3-way higher and 4-way, all ticked to start; at least one), then the PDF. The ticks can be changed later on the schedule. If a schedule needs signing to accept its terms, the same detection and jump-to fields are added.

### Contracts

- UI word is **contract** everywhere staff see it. Internal API/SQLite still use `envelopes`.
- Draft → bake → ready → send → client signs → completed. **Bake again** is available while the contract is ready and unsent, so a template fix does not need a new contract.
- **Only the client signs by link (item 37).** The contractor, the supplier (4-way) and the broker each have a saved signature on their record. **Send to the client** applies them in sign order (Contractor, Supplier, Broker), each dated as entered under **Dates signed** (item 41), then emails the client its link; the client signs last. Send stays blocked until each has a saved signature for the person named on the contract, and the contractor and supplier have their director ID on file.
- **3-way lower** and **3-way higher**: Contractor, Broker, Client. **4-way**: those three plus Supplier (SPV). Sign order is Contractor, Supplier when present, Broker, Client. The contract page and the contracts list show the type.
- The due diligence pack is built in the app. No party is emailed to complete it. Companies House and the sanctions check are fetched from the company number. Staff attach only the documents that cannot be fetched, enter the received and checked dates, compile the pack, and the broker signs it in the app. Send stays blocked until that signature.
- Documents already collected for the due diligence pack are not requested again. The client uploads its incorporation certificate, VAT certificate and director ID when it signs. The contractor’s and supplier’s director IDs are uploaded on their records and bound into the signed contract (not the pack). The broker attaches nothing.
- **Signature options (2026-11-25):** every signature (each party in the signing room, and the broker on the due diligence pack) can be drawn, typed, or uploaded. Typed offers six bundled handwriting fonts: Great Vibes, Dancing Script, Homemade Apple, Sacramento, Mr Dafoe, Herr Von Muellerhoff (OFL / Apache, self-hosted from `@fontsource`, Latin and Latin Extended). Upload takes a PNG, JPEG or WebP photo or scan, fades the paper to transparent and crops to the ink. All three become a cropped PNG in the browser, so the server stores and stamps them the same way. Only the method is kept (`signatures.method`, which decides whether a typed name or the image is stored); the font name is not recorded or printed anywhere (item 33). Signatures are stamped at their own proportions inside each signature box (they used to be stretched to fill it).
- **Contract cover:** the broker’s front cover keeps its title; the contract details fill its own text slots in the bottom-right quarter. No full-width stamped box. A cover made as a template (named text fields, item 36) is filled field by field instead.
- **Pack layout:** the broker’s front cover with the pack details drawn into its panel (or a generated cover in the same style), alternating branded headers, page numbers and the pack reference in the footer, bordered tables with Clear (green tick) / Flag (red cross) / N/A results, a divider page before each company’s annexes (headed like its Part), an annex index grouped by the same Part headings, annexes numbered 1–n, and every annex page framed and captioned “Annex n: Document, DD/MM/YYYY”. Layout helpers are in `server/src/packLayout.js`. The v7 brief (item 31) applies to 3-way and 4-way packs alike.
- Hash-chained event log kept in the database only (not shown or printed anywhere, item 33); baked PDF on disk.
- On completion, the signed PDF binds every requested attachment. There is no audit trail page. All parties get that same bound copy.

```bash

cat TUNNEL_URL.txt           # gitignored; do not commit

# Publish code changes WITHOUT changing the public URL
bash scripts/deploy-live.sh
```

Rules of the road:

- Prefer **localhost.run** `*.lhr.life` via `scripts/keep-tunnel-alive.sh`.
- Do **not** use Cloudflare `*.trycloudflare.com` quick tunnels.
- **Do not** kill/restart the tunnel during normal coding or status commits.
- Watchdog holds SSH open while local API is down (deploys); only recycles SSH if the process dies or public fails while local is healthy.
- “No tunnel here” = stale hostname after an SSH recycle — read a fresh URL from `TUNNEL_URL.txt`.
- Anonymous `*.lhr.life` hostnames still change if SSH itself dies; for a forever-stable host, add a named Cloudflare tunnel or localhost.run forever-free + SSH key later.
